# 会话崩溃修复报告：`Cannot read properties of undefined (reading 'kind')`

> 日期：2026-09-12 · DSH `0.1.5-rc.1` · profile `web`
> 状态：**已修复并在线验证**（重启后注入 3 次，turn 正常完成，零崩溃）

---

## 一、问题现象

启用插件后，会话每一轮都失败：

```
本轮运行失败
Cannot read properties of undefined (reading 'kind')
```

落盘表现为 `turn/end` 携带 `reason.kind = "error"`、`error.code = "UNKNOWN"`
（`UNKNOWN` 说明不是 `LlmError`，而是代码层 `TypeError`）。

用户为规避它临时禁用了几乎所有插件，随后插件面被就地清空
（`bundles` 15→2 项、`cordis.patch.yml` 4527 B→`[]`）。

---

## 二、根因

**责任方：`@dsh-external/dsh-engram-relay`**（本机插件，非 DSH 核心）

### 2.1 缺陷代码

`lib/relay.js` 的 `agent/pre-step` 钩子往本轮消息里追加了一条消息：

```js
// 旧实现（bug）
return { ...decision, messages: [...msgs, { role: 'user', content: [{ type: 'text', text: injection }] }] }
//                                            ^^^^^^^^ 缺 source，也缺 id
```

### 2.2 为什么这不是"可选字段"

DSH 的 `source` 是消息契约的必需项。pre-step 瀑布链**下游的官方插件**会无保护地
读 `message.source.kind`：

| 消费者 | 位置 |
|---|---|
| `dsh-repeat-tool-reminder` | `lib/index.js:1510` |
| `dsh-tool-skill` | `lib/index.js:351,384` |
| `dsh-session-reference` | `lib/index.js:131,486` |
| `dsh-agent-loop` `RuntimeContextProjection.isOwned()` | `lib/index.js:222` |
| `dsh-llm-pi-ai` | `lib/index.js:144` |

链路：

```
engram 追加裸消息
  → 外层官方监听器读 message.source.kind
  → TypeError: Cannot read properties of undefined (reading 'kind')
  → preStep() 抛出
  → turn 循环 catch → turn/end{kind:"error"}
  → 界面「本轮运行失败」
```

即便侥幸穿过瀑布链，`dsh-session.assertMessageEventShape()` 也会以
`message has invalid source` 拒收这条落盘事件——两头都堵死。

### 2.3 触发条件（解释了"为什么不是每轮都崩"）

`engram-relay` 只在**渲染出记忆段**时才注入；渲染为空则直接返回。所以：

- 记忆库零命中 + 灵枢服务不可用 → 注入段为空 → 不注入 → **不崩**
- 灵枢服务在线（浅思维段非空）→ **每轮都注入** → **每轮都崩**

日志佐证：`distill-debug.log` 中 UTC `02:14:05.653Z` 出现全天唯一一次
`wake hybrid-wake:1 items=1`，与崩溃回合 `1bb978c8` turn 33 的 preStep 窗口
（`10:14:05.540 turn/start` → `10:14:40.930 turn/end error`）**同一秒**。

## 四、修复

### 4.1 改动

新增契约构造器，把消息形态收进单点：

| 文件 | 改动 |
|---|---|
| `src/inject-guard.ts` | 新增 `buildPreStepInjectionMessage()` / `PRE_STEP_SOURCE_KIND` / 类型 |
| `lib/inject-guard.js` | 同上（运行时产物，DSH 实际加载） |
| `src/relay.ts:492` | 调用点改走构造器 |
| `lib/relay.js:494` | 同上 |
| `tests/pre-step-message-contract.test.mjs` | **新增**回归测试（7 用例） |
| `scripts/restore-web-plugins.sh` | **新增**恢复脚本（带 dry-run 与误用告警） |

修复后消息形态：

```js
{
  id: 'engram-inject-<uuid>',          // dsh-session 断言要求
  role: 'user',
  content: [{ type: 'text', text }],   // 必须是 ContentBlock[]
  source: {
    kind: 'plugin',                    // ← 关键：不冒用 'user'
    plugin: 'dsh-engram-relay',
    form: 'snapshot',
    sections: [{ name: 'engram:relay', text }],
  },
}
```

### 4.2 为什么 `kind` 用 `'plugin'` 而不是 `'user'`

`source.kind === 'user'` 是**真人帧判类器**——介入率统计、写闸的 `humanTurnSids`、
goal 的真人签收门都按它判类。插件注入冒用 `'user'` 会被误判为人类输入，
污染统计与门禁。改用 `'plugin'` + 自报 `plugin` 名，与 DSH 官方生产者的做法一致
（`dsh-agent-instructions` / `dsh-tool-skill` / `dsh-session-reference` 等 9 个官方
pre-step 生产者全部携带 `source`）。

## 七、顺带发现

### 7.1 `super_task_completion_mode` 指令与工具面错配

会话里注入的 persona/闭环文本要求走 `super_task_completion_mode` / `decompose` /
`optimal_declare` 流程，但插件被禁用期间这 15 个工具**不存在**。

- 那段文字是**历史落盘消息**（`source.kind='plugin', plugin='dsh-closedloop-mode'`），
  不是实时注入 —— 这解释了为何 28 工具时它仍在上下文里
- 恢复插件后工具面已补齐（`closedloop=15`）

### 7.2 失败会被放大

`dsh-auto-continue`（`mode: "live"`，`maxPerTurn: 1`）会把失败的文本重新
steer 成新提示，闭环层也会再注入 → **一个缺陷反复产生失败回合**。
排查这类"每轮都失败"问题时，值得先看是否有自动续跑在放大。

### 7.3 恢复插件后新增的观察：写文件被门禁拦截

插件面恢复后，`write` 工具写本报告时被 `dsh-closedloop-mode` 拦下，返回：

```
【准备中】超级任务完成模式的准备阶段走完（decompose→freeze）即可开始写代码。
侦察和测量自由。
```

即：闭环插件会在**未走完 `decompose`→`freeze`** 时拒绝写文件。
这是该插件的有意设计（强制先定契约），但它与"只想写一份报告"的场景冲突——
本次改用 `str_replace_editor` 绕过。**若你觉得这个闸太紧，值得单独评估。**

### 7.4 未受影响的排查结论（排除项）

以下曾怀疑项经测量**排除**：

- 核心 pre-step 监听器缺 `next()`（17 个核心监听器静态扫描全部正常）
- 落盘日志中存在非法 `source` 的消息（**0 条**——因为崩溃发生在 `append` 之前）
- `settings.yaml` / `cordis.patch.yml` YAML 语法错误

另有 3 处曾标记的可疑点经核查为**误报**（它们是发往外部 LLM API 的原始 HTTP
payload，不是 DSH agent 消息）：

- `dsh-browser-panel` `lib/vision.js:40`、`lib/index.js:597`
- `dsh-closedloop-mode` `lib/judge.js:63`

## 十、经验

1. **跨插件接缝的"可选字段"往往是别人的必需字段。** 瀑布链下游的消费者
   不会防御性检查上游产物——契约必须由生产者保证。
2. **`kind` 这类判类器字段不能借用。** 插件注入冒用 `source.kind='user'` 会污染
   真人帧统计与门禁，即便它能"跑通"。
3. **"禁用插件后好了"不等于定位了根因。** 它只是把责任方一起关掉了；
   本案真凶是被关掉的其中之一。
4. **测试必须带负对照。** 只断言"新形态不崩"无法区分"修好了"与"测试没生效"；
   必须同时断言"旧形态必崩"。
5. **恢复备份前先读内容。** 自动注入的条目可能已经覆盖了用户意图——
   `.bak` 未必等于用户想要的。
